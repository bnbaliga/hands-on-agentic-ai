Building a Multi-Agent System with LangGraph and Google Gemini
Introduction
It is sprint planning day at DevCorp. The engineering manager pulls you aside:

"We are shipping features too slowly. What if we had an AI team that reads requirement docs, writes code, and reviews it automatically?"

That is exactly what we are going to build - a pipeline of three coordinated AI agents working inside a LangGraph StateGraph, each doing one job and handing its output to the next.

What is a Multi-Agent System?
Instead of asking one LLM to do everything at once, we split the work into specialised roles. Each agent focuses on one task and builds on what the previous agent produced.

In this lab, three agents work in sequence:

Agent	Role
Planner	Reads the requirement doc via semantic search, produces a numbered implementation plan
Coder	Takes the plan and writes clean Python code
Reviewer	Audits the code against the requirement, plan, and code together
What is LangGraph?
LangGraph lets us build stateful, multi-step AI workflows as directed graphs.

Nodes are Python functions that do work
Edges define what runs next
State is a shared typed dictionary that every node reads from and writes to
[START] -> Planner -> Coder -> Reviewer -> [END]
Unlike LangChain's AgentExecutor which loops inside a single agent, LangGraph lets us define the structure of the workflow explicitly - which agent runs when, what it can see, and what it produces.

1. Problem Statement / Use Case Overview
A single LLM call asked to "read a spec and write working code" tends to skip steps, miss edge cases, or produce code that does not actually match the requirement. The fix is the same one engineering teams use on themselves: split the work into specialised roles, each doing one job well and handing its output to the next.

A basic agent does everything in one shot:

Requirement -> LLM -> Code
This notebook builds a three-agent pipeline instead:

Requirement -> Planner -> Plan -> Coder -> Code -> Reviewer -> Review
Planner: retrieves relevant sections of a requirements document via semantic search, then produces a numbered implementation plan.
Coder: turns that plan into actual Python code.
Reviewer: audits the code against the original requirement, the plan, and the code itself.
Unlike a reflection loop, this pipeline is linear, not cyclic: each agent runs exactly once, in a fixed order. There is no branch that sends work backward for revision; the emphasis here is on role separation and shared state, not iterative refinement.

This is built with LangGraph, which models the workflow as a state machine (StateGraph) with nodes and edges, rather than as three separate, disconnected LLM calls. Because Gemini is reached through this lab's own proxy rather than Google's public endpoint, the notebook also wires up two separate Gemini clients: a LangChain chat model for the three agents, and a lower-level SDK call for embeddings.

2. Input Data
Two inputs feed the pipeline:

Requirements PDF: SecurEnvoy-RESTful-API-Guide.pdf, loaded, chunked, and embedded into a vector store so the Planner can retrieve relevant context instead of relying on the requirement text alone.

User requirement: a plain-text description of the feature to build, defined at run time, e.g.:

Build a Python REST API endpoint that accepts a user's name and email,
validates the input, stores the record in a SQLite database,
and returns a confirmation JSON response.
The same graph can be re-run with any other requirement string by changing initial_state["requirement"].

3. Processing
The workflow is a graph with three nodes run once each, in a straight line:

Planner node: embeds the requirement, retrieves the top-k matching chunks from the requirements PDF, and asks the LLM for a 5–8 step implementation plan (no code yet).
Coder node: takes only the plan and asks the LLM to write PEP 8-compliant Python implementing it, with type hints and docstrings.
Reviewer node: sees the requirement, plan, and code together, and produces a structured review (alignment, correctness, style, improvements, verdict).
START -> planner -> coder -> reviewer -> END
There is no router and no loop back: each node reads the state fields it needs and writes new ones forward. Retrieval happens once, inside the planner node, before any code is written.

4. Output
Running app.invoke(initial_state) returns the final GraphState with every field populated:

retrieved_chunks: the PDF passages the Planner pulled in
plan: the numbered implementation plan
code: the generated Python implementation
review: the structured review, ending in an APPROVED / NEEDS REVISION verdict
A print_section helper prints each of these under a labelled header so the full pipeline output (retrieval, plan, code, review) is visible in one pass. The notebook also renders the compiled graph as a Mermaid diagram before running it.

6. Underlying Concepts
GraphState (TypedDict) and node isolation: the shared state schema (requirement, retrieved_chunks, plan, code, review) that every node receives in full but updates only in part - LangGraph merges the returned fields back in. Because each node reads only the fields it actually needs (the Coder never sees retrieved_chunks, only plan), every agent's prompt stays focused and its context stays clean.
Fixed edges vs. conditional edges: this graph uses only fixed edges (add_edge), so execution order is set in advance, in contrast with a reflection-style graph, where a conditional edge routes back to an earlier node based on a runtime decision.
Retrieval-augmented planning and chunking: the Planner doesn't plan from the raw requirement alone; it first retrieves the top-k semantically similar chunks from the requirements PDF via retriever.invoke(requirement). Those chunks come from RecursiveCharacterTextSplitter, which splits PDF pages into 600-character chunks with 100-character overlap so each chunk stays focused on a single requirement, grounding the plan in the actual spec.
Two Gemini clients behind one proxy: the LLM (llm) is a ChatGoogleGenerativeAI pointed at the lab's endpoint via base_url. Embeddings go through a separate CustomGeminiEmbeddings wrapper that calls the legacy google.generativeai.embed_content() function directly, using the module-level configuration set up once in Step 1 (genai.configure(..., transport="rest", client_options=...)). The newer GoogleGenerativeAIEmbeddings client is also instantiated as _embedding_client in Step 2, but it is never actually used to embed anything - the pipeline's real embedding path is CustomGeminiEmbeddings.
extract_text() helper: normalises .content from the LLM response, which can come back as either a plain string or a list of {"text": ...} parts depending on the response, into a plain string every node can use consistently.
app.invoke(...): runs the compiled graph end-to-end and returns the final state, as opposed to app.stream(...), which would yield intermediate state after each node.

Step 2: Initialize the Gemini LLM and embeddings
One llm instance is shared by all three agent nodes - each node's "role" comes from its own prompt-building function, not a separate model instance. Embeddings are handled differently: CustomGeminiEmbeddings wraps the legacy genai.embed_content() call (using the GEMINI_EMBEDDING_MODEL constant from Step 1), because the lab's proxy needs that direct REST-configured path. The LangChain-native GoogleGenerativeAIEmbeddings client is also created here as _embedding_client, but it isn't used further down - embeddings = CustomGeminiEmbeddings() is what actually backs the vector store. extract_text() normalises whatever shape Gemini's response comes back in into a plain string every node can use.


from langchain_core.embeddings import Embeddings
from langchain_google_genai import ChatGoogleGenerativeAI, GoogleGenerativeAIEmbeddings

llm = ChatGoogleGenerativeAI(
    model="gemini-3.5-flash",
    google_api_key=GOOGLE_API_KEY,
    base_url=ENDPOINT_URL,
)

_embedding_client = GoogleGenerativeAIEmbeddings(
    model="gemini-embedding-001",
    google_api_key=GOOGLE_API_KEY,
    base_url=ENDPOINT_URL,

from langchain_core.vectorstores import InMemoryVectorStore
 
class CustomGeminiEmbeddings(Embeddings):
    def __init__(self, model=None):
        self.model = GEMINI_EMBEDDING_MODEL
 
    def embed_documents(self, texts):
        return [self.embed_query(text) for text in texts]
 
    def embed_query(self, text):
        response = genai.embed_content(model=self.model, content=text)
        return response["embedding"]
 
embeddings = CustomGeminiEmbeddings()
vectorstore = InMemoryVectorStore(embedding=embeddings)

def extract_text(response) -> str:
    """Normalise a ChatGoogleGenerativeAI response into a plain string."""
    content = response.content
    if isinstance(content, str):
        return content
    if isinstance(content, list):
        return "".join(part.get("text", "") for part in content if isinstance(part, dict))
    return str(content)
Step 3: Define the shared state
This is the single object that flows through every node in the graph.


from typing import TypedDict

class GraphState(TypedDict):
    requirement:      str   # raw requirement text entered by the user
    retrieved_chunks: str   # relevant PDF sections retrieved by the Planner
    plan:             str   # numbered implementation plan - written by Planner
    code:             str   # Python code - written by Coder
    review:           str   # structured code review - written by Reviewer
Step 4: Load requirements into a vector store
This builds a retriever the Planner can query for the top-4 most relevant chunks of the spec, so its plan is grounded in the actual document rather than the requirement text alone. It reuses the embeddings object created in Step 2, and reads the PDF back from the plain filename it was uploaded under.


import os
from pypdf import PdfReader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.documents import Document
from langchain_core.vectorstores import InMemoryVectorStore

PDF_PATH = "SecurEnvoy-RESTful-API-Guide.pdf"


def load_requirements(pdf_path: str) -> list:
    if not os.path.exists(pdf_path):
        raise FileNotFoundError(f"Could not find '{pdf_path}'.")

    reader = PdfReader(pdf_path)
    pages = [
        Document(page_content=page.extract_text() or "", metadata={"page": i + 1})
        for i, page in enumerate(reader.pages)
    ]

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=600, chunk_overlap=100,
        separators=["\n\n", "\n", " ", ""]
    )
    chunks = splitter.split_documents(pages)
    print(f"Loaded {len(pages)} pages → {len(chunks)} chunks")
    return chunks


def build_index(chunks: list):
    vectorstore = InMemoryVectorStore(embedding=embeddings)
    vectorstore.add_documents(chunks)
    print("In-memory vector index ready.")
    return vectorstore.as_retriever(search_kwargs={"k": 4})


chunks    = load_requirements(PDF_PATH)
retriever = build_index(chunks)
Step 5: Define the planner node
The retrieval step runs first, inside the node, so the plan is written with actual spec context in front of the model.


def planner_node(state: GraphState) -> dict:
    requirement = state["requirement"]

    docs = retriever.invoke(requirement)
    retrieved_chunks = "\n\n".join([
        f"[Chunk {i+1} | page {doc.metadata.get('page', '?')}]\n{doc.page_content}"
        for i, doc in enumerate(docs)
    ])

    prompt = f"""You are a senior software architect at DevCorp.

Requirement: \"\"\"{requirement}\"\"\"

Retrieved context from the requirements document:
{retrieved_chunks}

Produce a clear, numbered implementation plan with 5-8 steps.
Each step must be specific and actionable. Do NOT write code yet.
"""
    plan = extract_text(llm.invoke(prompt))
    print("[Planner] Done.\n", plan)
    return {"retrieved_chunks": retrieved_chunks, "plan": plan}
Step 6: Define the coder node
Notice the Coder only reads state["plan"]; it never sees retrieved_chunks. It doesn't need the raw spec text, only the plan derived from it.


def coder_node(state: GraphState) -> dict:
    prompt = f"""You are a senior Python developer at DevCorp.

Implementation plan:
{state["plan"]}

Write clean, PEP 8-compliant Python code that implements this plan exactly.
Include type hints, docstrings, and inline comments explaining each step.
"""
    code = extract_text(llm.invoke(prompt))
    print("[Coder] Done.\n", code)
    return {"code": code}
Step 7: Define the reviewer node
The Reviewer is the only node that sees all three pieces at once (requirement, plan, and code), since auditing alignment requires comparing them against each other.


def reviewer_node(state: GraphState) -> dict:
    prompt = f"""You are a principal engineer at DevCorp conducting a code review.

Requirement: \"\"\"{state["requirement"]}\"\"\"
Plan: {state["plan"]}
Code: {state["code"]}

Write your review under these exact headings:
1. Alignment - does the code implement all plan steps? What is missing?
2. Correctness - are there bugs, edge cases, or incorrect logic?
3. Style - PEP 8 compliance, docstrings, naming conventions?
4. Improvements - 2-3 concrete suggestions with short code examples.
5. Verdict - APPROVED or NEEDS REVISION, with one sentence of justification.
"""
    review = extract_text(llm.invoke(prompt))
    print("[Reviewer] Done.\n", review)
    return {"review": review}
Step 8: Assemble and compile the graph
All four edges are fixed; there's no conditional routing here, since each agent always runs exactly once.


from langgraph.graph import StateGraph, START, END

graph_builder = StateGraph(GraphState)

graph_builder.add_node("planner",  planner_node)
graph_builder.add_node("coder",    coder_node)
graph_builder.add_node("reviewer", reviewer_node)

graph_builder.add_edge(START,      "planner")
graph_builder.add_edge("planner",  "coder")
graph_builder.add_edge("coder",    "reviewer")
graph_builder.add_edge("reviewer", END)

app = graph_builder.compile()
print("StateGraph compiled.")
print("Flow: START → planner → coder → reviewer → END")

11. What We Learnt
This notebook built a linear multi-agent pipeline using LangGraph: a StateGraph held a shared GraphState, and three specialised nodes (Planner, Coder, Reviewer) each read only the state fields they needed and wrote new ones forward, in a fixed order with no loops. The Planner additionally used retrieval-augmented generation, pulling relevant chunks from an embedded requirements PDF before drafting its plan, so the whole pipeline was grounded in an actual spec rather than the user's requirement text alone.

StateGraph: defines nodes and edges over a shared, typed state object
Fixed edges: set execution order in advance, as opposed to conditional edges that enable loops
Node isolation: each agent reads only the state fields relevant to its job, keeping prompts focused
Retrieval-augmented planning: grounding an agent's output in retrieved document chunks rather than raw user input alone
Role specialisation: splitting a single "read spec and write code" task into Planner → Coder → Reviewer improves the quality and auditability of the result over one monolithic LLM call
